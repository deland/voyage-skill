# VoyageSkill v0.1 产品与系统设计提案

> 状态：已由 User 于 2026-08-13 全部确认；已拆分为正式领域真源
>
> 日期：2026-08-13
>
> 本文保留为第一阶段设计记录，不是项目运行真源。当前生效内容见 `docs/truth-registry.json` 和 `docs/decisions/D-0001-v0.1-baseline.md`。

## 1. 设计依据与边界

本提案以 `docs/research/` 下的 Graph Engineering 材料为研究输入，继承其中的系统原则，但不继承旧项目的路径、命令、供应商、运行状态或固定角色结构。

必须保持以下约束：

1. Skill 只负责发现、冷启动和恢复，不保存项目动态状态。
2. 项目被建模为节点、边、资源、门禁、通道和外部锚点组成的运行图。
3. 执行、质量、治理、审计是相互制约的四类反馈回路，不是四个固定职位。
4. 状态只由命令结果、不可变锚点和真实读回证明。
5. 文件之外的账号、端口、环境和会话也是受控资源。
6. 异步动作只能引用不可变对象。
7. 规则必须经过“提出 → 批准 → 应用 → 验证”，并支持退役。
8. 快回路无权改写慢回路确定的目标、真源和强制门禁。
9. 高风险和不可逆动作必须由 User 最终授权。
10. 系统必须支持跨会话恢复，并允许按风险压缩流程。

## 2. 产品定位

### 2.1 一句话定位

VoyageSkill 是一个面向长周期、多 Agent 软件项目的项目级运行控制系统：它用精简 Skill 作为稳定入口，用项目文档和追加式账本承载真源，以可验证的运行图协调任务、资源、权限、门禁、证据、恢复与规则演化。

### 2.2 目标用户

- 同时协调多个 Agent、工具或人工参与者的项目负责人；
- 需要跨会话、跨天或跨版本持续推进的软件项目；
- 存在共享账号、端口、环境、数据库、浏览器会话或发布窗口的团队；
- 对生产、持久数据、费用、安全或外部写入有明确授权要求的项目。

### 2.3 核心价值

- **可恢复**：新会话可从真源、账本和证据重建状态，不依赖上一个 Agent 的记忆。
- **可验证**：交付、评审、测试和运行读回指向同一不可变对象。
- **可约束**：资源、权限、门禁和风险升级路径是运行图的一部分。
- **可纠错**：质量可以否决执行，审计可以纠正治理，User 可以裁决高风险冲突。
- **可演化**：规则的新增、修改和退役都有独立批准与验证。

### 2.4 产品形态原则

VoyageSkill 不是一篇巨型提示词。最终产品至少包含两个逻辑部分：

1. **稳定入口**：精简的 `SKILL.md`，只说明发现顺序、恢复协议、必要判据和真源指针；
2. **项目运行包**：由项目文档、机器可校验的系统图、追加式账本、资源状态和证据组成。

是否同时提供确定性 CLI、库或服务，由 User 在开发前决定。无论采用哪种载体，Skill 都不能成为动态状态数据库。

## 3. 非目标

VoyageSkill v0.1 不以以下事项为目标：

- 复制 DevSwarmSkill 或预设 Product Manager、Architect、Developer、Reviewer 等固定角色槽位；
- 规定某个模型、Agent 供应商、消息平台、代码托管平台或云服务；
- 自动替代 User 做高风险、不可逆、生产、费用或安全决策；
- 成为通用项目管理平台、Issue Tracker 或聊天系统；
- 自动证明 Agent 身份、诚实性或所有外部系统的真实性；
- 在第一版实现图形化控制台、跨项目联邦、复杂调度优化或自主组织扩缩容；
- 将研究文档、会话摘要、Worker 自报或“最新修改的文件”自动提升为真源；
- 为所有低风险小任务强制运行同等重量的完整流程；
- 在缺乏真实事故和验证证据时固化大量永久规则。

## 4. 最小可行使用场景

### 4.1 场景 A：跨会话接班

一个新 Agent 进入项目后：

1. 通过 Skill 找到真源注册表、当前账本和恢复手册；
2. 校验真源版本和账本完整性；
3. 读取未完成工作、活动资源租约、阻塞、等待中的 User 决策和最近证据；
4. 对易变状态执行实时探测；
5. 输出“已证明、仅声明、未知、冲突”四类状态，而不是复述旧会话摘要。

成功标准：不读取上一会话记忆，也能确定当前可安全继续的工作和不能继续的原因。

### 4.2 场景 B：不可变交付与独立质量否决

执行回路领取一个已授权工作项和资源，产出不可变交付锚点。质量回路只针对该锚点执行评审与测试，并记录完整结果。如果失败，交付被否决；修复必须产生新锚点，旧质量结论不得自动沿用。

成功标准：执行者的完成声明不能使工作项进入“已接受”；异步评审与测试不会因分支移动而漂移。

### 4.3 场景 C：共享资源冲突控制

两个工作项竞争同一文件、账号、端口、环境或会话。系统根据资源策略拒绝第二次冲突领取，或将其排队。对于易变外部资源，派发前重新探测实际持有人和可用性。

成功标准：静态登记不被误当作实时可用；租约过期、异常残留和手动占用都有明确恢复路径。

### 4.4 场景 D：审计阻塞与规则演化

审计回路发现一个重复失败来自错误验收标准或失效门禁，而非执行者。它可以用证据阻塞最小受影响范围，提出规则变更，但不能独立批准、应用并验证自己的提案。

成功标准：治理问题回到治理回路修复；规则生效与规则有效被分别记录；错误阻塞有独立申诉路径。

### 4.5 场景 E：高风险动作升级

工作项涉及生产部署、持久数据修改、不可逆操作、显著费用、安全权限、外部公开写入或放宽强制门禁。系统停止在安全状态，向 User 提交最小决策项，只有记录了明确授权后才允许继续。

成功标准：没有 User 授权锚点时，高风险动作不能仅凭治理者或执行者声明进入可执行状态。

## 5. 真源层级与冲突规则

### 5.1 真源不是单一文件

VoyageSkill 采用“按领域分治、按权限生效”的真源体系，不使用简单的“最后修改者获胜”。建议的层级如下：

| 层级 | 内容 | 建议载体 | 生效权限 |
| --- | --- | --- | --- |
| L0 外部授权 | User 的产品裁决、高风险授权、例外批准 | 可引用的 User 决策记录 | 高风险和不可逆动作仅 User；其他事项可由 User 限定范围委托 |
| L1 规范合同 | 产品目标、非目标、风险边界、架构与公共合同、强制治理规则 | `docs/product/`、`docs/governance/`、`docs/architecture/` | 对应领域的批准流程 |
| L2 系统结构 | 节点类型、边语义、权限、状态机、门禁与资源策略 | `docs/system/` 及机器可校验 Schema | 治理批准；重大变更需 User |
| L3 操作协议 | 冷启动、派发、验证、恢复、读回、升级和事故处理 | `docs/operations/` | 治理批准，不能放宽上层约束 |
| L4 运行事实 | 工作事件、资源租约、交付锚点、测试结果、读回、阻塞和决策引用 | 追加式账本与证据存储 | 由有权限的回路追加，不能改写历史 |
| L5 稳定入口 | 发现顺序、恢复入口、真源指针 | `SKILL.md` | 只指向真源，不复制动态状态 |

`docs/research/` 永远属于研究输入，不自动进入上述真源层级。

### 5.2 冲突解析

遇到冲突时按以下顺序处理：

1. 先识别冲突所属领域和作用范围，不能跨领域用一个“最新文件”覆盖另一个真源；
2. 检查候选来源是否处于已批准、已生效且未被替代的状态；
3. 同一领域内，明确记录的 User 决策优先于下层决定；
4. 下层操作协议不能修改上层产品、架构、风险或强制门禁；
5. 运行读回描述“实际是什么”，规范合同描述“应该是什么”；两者不互相覆盖，偏差应产生阻塞或纠偏工作项；
6. 研究、草稿、会话记忆、Worker 总结和未验证推断只可作为线索；
7. 无法确定优先级或生效状态时，停止受影响范围并升级，不做静默猜测。

### 5.3 变更与退役

- 真源变更必须包含版本、作用范围、批准者、生效时间和被替代对象；
- 旧版本保留历史可追溯性，但从当前发现路径中退役；
- 删除不是默认退役方式；应先记录 `supersedes` 或 `retires` 关系；
- Skill 中的指针变更只能反映已生效真源，不能使草稿自动生效。

## 6. 系统图数据模型

### 6.1 基本记录

每个节点至少包含：

- `id`：项目内稳定、不可复用的标识；
- `type`：节点类型；
- `version`：定义版本；
- `status`：受该类型状态机约束的状态；
- `scope`：适用项目、工作项、环境或资源范围；
- `authority`：谁可以创建、变更、批准或关闭；
- `provenance`：创建者、时间、来源和因果引用；
- `risk`：风险等级和触发原因；
- `evidence_refs`：支持当前事实的证据引用；
- `supersedes`：替代或退役关系。

每条边至少包含：

- `id`、`type`、`from`、`to`；
- 生效前置条件；
- 允许创建该边的权限；
- 必需证据；
- 失效条件；
- 失败后的状态转移或升级目标。

### 6.2 最小节点类型

| 节点 | 作用 |
| --- | --- |
| `project` | 运行图边界与项目标识 |
| `principal` | 人、Agent 或受控工具身份；不等同于固定职位 |
| `loop-binding` | 某主体在特定范围内承担执行、质量、治理或审计权限 |
| `truth-source` | 领域真源及其版本、生效和写权限 |
| `decision` | User 或获授权主体作出的可引用决定 |
| `work-item` | 有范围、非目标、风险、依赖和验收标准的工作单元 |
| `delivery` | 某工作项的一次交付尝试 |
| `immutable-anchor` | commit、tag、制品摘要、内容哈希或精确 diff |
| `evidence` | 命令结果、评审、测试、读回或人工验收证明 |
| `gate` | 进入下一状态前必须满足的判据 |
| `resource` | 文件、账号、端口、环境、会话等受控对象 |
| `lease` | 对资源在限定时间和范围内的持有事实 |
| `environment` | 可读回版本、配置、数据水位和健康状态的运行环境 |
| `channel` | 任务投递、消息、Agent 会话或人工批准通道 |
| `rule` | 有生命周期、范围、成本和验证方式的规则 |
| `block` | 带证据、最小作用范围和解除条件的阻塞 |
| `external-anchor` | User 结果、真实环境或其他不能由当前执行者自行改写的校准点 |

### 6.3 最小边类型

| 边 | 语义 |
| --- | --- |
| `governs` | 真源、决定或规则约束某对象 |
| `depends-on` | 工作项、门禁或资源依赖 |
| `authorized-by` | 动作由某决定或权限授权 |
| `bound-to-loop` | 主体在给定范围内承担某回路 |
| `assigned-to` | 工作项被派给主体；不代表已送达或已开始 |
| `delivered-via` | 投递通过某通道发生 |
| `acknowledged-by` | 接收方已确认收到 |
| `claims` / `releases` | 主体取得或释放资源租约 |
| `produces` | 工作项或动作产生交付、证据或锚点 |
| `anchored-at` | 交付、评审、测试或部署绑定不可变对象 |
| `validated-by` | 对象由质量证据验证 |
| `rejects` | 质量结论否决某次交付 |
| `blocks` / `unblocks` | 审计、门禁或风险阻塞与解除某范围 |
| `supersedes` / `retires` | 新版本替代或退役旧对象 |
| `readback-of` | 证据是某环境或资源的真实读回 |
| `escalates-to` | 超权或高风险事项升级到更高权限主体 |

### 6.4 系统不变量

1. 任何异步评审、测试、合流或部署都必须存在 `anchored-at` 边。
2. 同一交付的执行主体不能签发最终质量通过结论。
3. 没有证据引用的声明不能推进权威状态。
4. 强制门禁失败时不能创建接受或发布边。
5. 资源冲突策略不允许的两个活动租约不能同时成立。
6. 高风险动作没有有效 `authorized-by` User 决定时不能进入执行态。
7. 修复必须产生新交付和新锚点；旧结论不会自动继承。
8. 审计阻塞必须包含最小范围、证据、解除条件和申诉目标。
9. 历史事件不能原地修改；纠错通过追加反向或替代事件完成。
10. 任何派发都必须区分“已发送”“已确认收到”和“已开始执行”。

## 7. 四层回路及权限

四层回路是权限与反馈类型，可以由不同的人、Agent 或工具动态承担，不形成固定角色组织图。

| 回路 | 可以做 | 不可以做 |
| --- | --- | --- |
| 执行 | 接受已授权工作；领取资源；实现、自测；产出交付锚点和已知风险 | 自行宣布最终完成；签发本交付的最终质量通过；修改范围、真源、强制门禁或高风险授权 |
| 质量 | 独立评审与测试；检查 skip、假数据和真实路径；签发通过或否决；要求新锚点 | 修改被审交付后继续沿用原结论；用治理压力覆盖失败；把无证据声明记为通过 |
| 治理 | 定义范围、依赖、风险、资源、门禁、回路绑定、合流顺序和验收条件；维护规范真源 | 替代质量签字；静默修改交付；绕过 User 授权；在看到结果后追溯性降低判据 |
| 审计 | 检查执行、质量和治理；识别系统性失效；提出规则；用证据阻塞最小范围；推动规则退役 | 同时提出、批准、应用和验证自己的规则；裁决针对自身的申诉；无边界地阻塞整个项目 |
| User（外部） | 裁决产品目标、高风险冲突、不可逆动作、例外和审计申诉 | 不属于四层回路；其决定仍需记录范围和引用，避免后续会话误读 |

### 7.1 最小职责隔离

- 同一交付：执行签字与最终质量签字必须由不同主体完成；
- 同一规则：提出者不能独立批准；应用者不能独立完成有效性验证；
- 同一审计争议：阻塞发起者不能作为最终申诉裁决者；
- 同一高风险动作：执行者和治理者均不能替代 User 授权；
- 同一门禁：门禁定义、执行结果和例外批准必须保留独立记录。

### 7.2 按风险压缩

| 模式 | 适用条件 | 可压缩项 | 不可压缩项 |
| --- | --- | --- | --- |
| 轻量 | 低影响、可逆、无共享高风险资源 | 使用预批准的治理模板，减少逐项治理动作；审计按触发运行 | 四类权限边界、不可变锚点、关键证据、执行与最终质量隔离、授权边界 |
| 标准 | 常规多 Agent 开发与共享资源 | 审计可按事件或周期触发 | 独立质量、资源租约、门禁、账本和恢复 |
| 严格 | 生产、数据、安全、费用、外部写入或不可逆操作 | 不压缩 | 四层权限隔离、完整门禁、真实读回和 User 授权 |

风险不明、证据缺失或角色对分类有异议时，自动采用更严格模式。

## 8. 状态账本

### 8.1 账本原则

- 账本是追加式事件记录，不是可随意改写的状态表；
- 当前状态是由有效事件、真源版本和实时读回计算出的派生视图；
- 会话摘要可以链接账本，但不能向账本反向授予权威；
- 人工声明只能产生“已声明”事实，不能自动产生“已证明”事实。

### 8.2 三类状态

| 类别 | 含义 | 例子 |
| --- | --- | --- |
| 计划状态 | 系统希望发生什么 | 计划分配 Worker A、计划使用端口 8000 |
| 声明状态 | 主体报告发生了什么 | Worker 报告完成、报告已释放账号 |
| 观测状态 | 命令、锚点或读回证明了什么 | commit 存在、端口监听者、环境版本、测试完整统计 |

权威状态转移优先依赖观测状态。声明与观测冲突时保留两者，并将对象标记为冲突或阻塞。

### 8.3 事件最小字段

- 事件 ID、时间、主体和主体所承担的回路；
- 事件类型、目标对象、前序事件或因果链；
- 输入状态与期望输出状态；
- 不可变锚点和证据引用；
- 风险级别、授权引用和资源租约引用；
- 结果：成功、失败、部分完成、未知或冲突；
- 对历史错误的撤销、替代或纠正引用。

### 8.4 工作项最小状态机

```text
draft
  -> authorized
  -> ready
  -> active
  -> delivered(anchor)
  -> quality-passed
  -> accepted
  -> closed
```

允许的旁路状态包括：`blocked`、`rejected`、`awaiting-user`、`canceled` 和 `superseded`。

- `delivered` 必须引用不可变锚点；
- `quality-passed` 必须引用独立质量证据；
- `accepted` 必须满足全部强制门禁；
- `rejected` 返回执行时必须创建新的交付尝试；
- `blocked` 必须记录范围、原因、证据和解除条件；
- `awaiting-user` 表示系统已停止在安全状态，不能被普通重试绕过。

### 8.5 恢复视图

跨会话恢复至少输出：

- 当前有效真源及版本；
- 活动、阻塞和等待 User 的工作项；
- 每个工作项的最后不可变锚点和质量结论；
- 活动或疑似残留的资源租约；
- 必须实时复查的环境、账号、端口和会话；
- 未解决的真源冲突、审计阻塞和规则提案；
- 可以安全执行的下一步，以及每一步所需权限。

## 9. 资源模型

### 9.1 资源类型

| 类型 | 例子 | 默认策略 |
| --- | --- | --- |
| 文件资源 | 文件、目录、Schema、迁移编号、共享清单 | 单写者；只读可共享 |
| 账号资源 | 测试账号、云账号、发布身份 | 串行或按隔离账号分片；账本不保存秘密 |
| 端口资源 | 本地监听端口、调试端口 | 独占并实时探测持有人 |
| 环境资源 | 数据库、测试环境、预发、生产 | 按环境定义共享、串行或独占；写操作需门禁 |
| 会话资源 | Agent 会话、浏览器登录、远程 shell | 区分通道、登录态和执行会话；支持存活探测 |
| 时间窗口 | E2E 窗口、迁移窗口、发布窗口 | 串行或配额控制 |
| 配额资源 | 模型额度、API 额度、费用预算 | 计量、上限和 User 授权 |

### 9.2 资源记录

每个资源定义至少包含：

- 稳定 ID、类型、作用范围和风险级别；
- 并发模式：`exclusive`、`shared-read`、`serialized` 或 `rebuildable`；
- 冲突键和冲突判定规则；
- 实时探测方法及探测新鲜度；
- 领取权限、租约期限、续租和释放条件；
- 异常回收、清理和人工接管流程；
- 关联门禁与禁止动作；
- 对账号和凭据只保存秘密引用，不保存秘密值。

### 9.3 租约生命周期

```text
requested -> probed -> granted -> active -> released
                              \-> expired -> recovery-required
                              \-> conflicted -> blocked
```

资源注册表只说明“有什么资源、如何冲突”；实际可用性必须由新鲜探测和活动租约共同判断。租约过期不等于外部资源已经释放，必须根据资源类型执行恢复探测。

## 10. 门禁、证据和运行读回

### 10.1 门禁定义

每个门禁至少声明：

- 保护的状态转移；
- 适用范围和风险级别；
- 执行主体与签字权限；
- 输入不可变锚点；
- 命令或人工判据；
- 完整结果格式，包括通过、失败、跳过和未知；
- 失败、超时和不可执行时的去向；
- 是否允许例外，以及谁能批准例外。

### 10.2 证据适配

证据没有跨领域通用的单一强弱顺序。门禁必须先声明要证明的事实，再要求与该事实匹配的证据：

| 要证明的事实 | 适配证据 |
| --- | --- |
| 动作获得授权 | 可引用的 User 或有效委托决定 |
| 评审对象身份 | commit、tag、制品摘要、内容哈希或精确 diff |
| 命令执行结果 | 完整退出状态、标准输出、错误输出和统计 |
| 测试覆盖情况 | 总数、通过、失败、跳过、未执行及必要的变异验证 |
| 环境实际状态 | 真实环境的版本、配置、数据水位、健康与关键路径读回 |
| 产品结果 | User 验收或真实用户结果 |
| 规则是否有效 | 独立验证和后续真实交付结果 |

User 授权能够证明“允许执行”，但不能证明动作已经正确完成；真实读回能够证明环境状态，但不能反向授予权限。主体声明、会话摘要和推断只能作为线索，不能单独满足权威门禁。

### 10.3 运行读回

涉及环境变更时，应分别证明：

- 命令是否成功；
- 服务是否健康；
- 当前运行制品是否为目标锚点；
- 配置指纹是否正确；
- 数据或迁移水位是否正确；
- 登录、权限和关键用户路径是否可用；
- 日志、指标和告警是否处于允许状态。

“部署命令退出为 0”只能证明过程的一部分，不能等同于发布完成。

## 11. 规则生命周期与审计阻塞

### 11.1 规则状态机

```text
proposed -> approved -> applied -> verified -> active
                \-> rejected
                         \-> verification-failed -> revise-or-rollback
active -> deprecated -> retired
active -> superseded
```

规则至少记录：来源事故或新知、适用范围、预期收益、执行成本、风险、批准者、应用位置、验证方法、成功指标、失效条件和回滚方式。

### 11.2 审计阻塞

审计可以创建阻塞，但必须同时提供：

- 直接证据；
- 最小受影响对象和禁止动作；
- 为什么普通质量失败不足以处理；
- 客观解除条件；
- 复查时间或触发事件；
- 申诉目标；
- 审计者与争议行为的独立性说明。

审计不能仅以“最佳实践”或无边界风险为由阻塞整个项目。证据不足时可以提出调查工作项，但不能伪装成已证明缺陷。

### 11.3 规则退役

- 定期检查规则是否仍有触发、是否重复、是否产生过高成本；
- 规则无效、被更高层机制替代或风险消失时进入 `deprecated`；
- 退役前确认移除不会重新打开已知风险；
- 退役本身需要批准和验证，但不要求保留无意义的永久门禁；
- 历史规则保留可追溯记录，不再进入活动发现路径。

## 12. 第一版范围

### 12.1 v0.1 必须具备

1. 精简项目级 Skill 入口与确定性冷启动顺序；
2. 真源注册、版本、生效、替代和冲突规则；
3. 节点、边、权限和状态机的最小 Schema；
4. 追加式事件账本及可重建的当前状态视图；
5. 文件、账号、端口、环境和会话的统一资源定义与租约；
6. 工作项、交付、不可变锚点和独立质量结论；
7. 门禁、完整测试统计、证据等级和运行读回记录；
8. 执行、质量、治理、审计四种回路权限与职责隔离校验；
9. 规则提出、批准、应用、验证、替代和退役；
10. 审计最小范围阻塞、解除和申诉；
11. 风险分类、流程压缩和 User 授权记录；
12. 跨会话恢复与结构一致性验证。

### 12.2 v0.1 明确不做

- 图形化 UI 和实时协作服务器；
- 自动创建、终止或路由任意供应商 Agent；
- 分布式锁、跨机器共识和多项目联邦；
- 内置秘密存储或凭据代理；
- 直接执行生产部署、数据库迁移或外部付费动作；
- 自动生成永久规则；
- 复杂成本优化、信誉评分和 Worker 排名；
- 每日外部研究自动化；
- 与特定 Issue Tracker、Git 平台或云厂商深度绑定。

## 13. 开发计划

当前阶段只完成方案确认，不编写实现代码。User 确认后按以下顺序开发。

### M0：产品与授权基线

交付：获批的产品合同、非目标、术语、风险分类、User 授权边界和决策记录。

验收：所有后续 Schema 和流程都能指向明确的上层决定；研究输入与运行真源已明确隔离。

### M1：真源与运行图规范

交付：真源注册规范、最小节点/边 Schema、状态机、权限矩阵、证据模型和冲突算法。

验收：可用固定样例验证无锚点异步动作、越权状态转移、自证质量和无证据状态会被拒绝。

### M2：账本与确定性验证器

交付：追加式事件格式、派生状态规则、结构验证器、冲突报告和恢复快照。

验收：删除会话上下文后，仅凭项目文件可重建相同状态；修改历史或制造断裂因果链会被检测。

### M3：资源、门禁与读回

交付：资源注册、租约生命周期、实时探测接口、门禁结果、证据引用和环境读回模型。

验收：能够阻止已注册的冲突租约，识别过期但未证明释放的资源，并区分命令成功与环境正确。

### M4：四层回路与规则治理

交付：回路绑定、职责隔离、风险压缩配置、审计阻塞、申诉以及规则全生命周期。

验收：执行者不能签发自身最终质量通过；审计不能裁决自身申诉；未获 User 授权的高风险动作被阻止。

### M5：Skill 入口与参考项目

交付：精简 `SKILL.md`、按需加载的参考资料、冷启动/恢复流程和不依赖供应商的示例项目。

验收：全新会话可从 Skill 找到正确真源并恢复；Skill 不含项目动态状态或大段重复规范。

### M6：独立验证与试运行

交付：正常、否决、资源冲突、审计纠正治理、高风险升级和规则退役的端到端用例。

验收：独立验证者能复现结果；失败会定位到执行、质量、治理、审计、资源、通道或环境中的正确层，而非一律归因于 Worker。

## 14. 需要 User 决定的问题

以下 D1–D8 会影响第一版架构，建议在编码前确认。

### D1. 第一版产品载体

建议：**项目级 Skill + 项目内确定性 CLI**。Skill 负责发现与流程，CLI 负责 Schema、账本、资源和门禁校验；暂不建设常驻服务。

需要决定：是否接受这一组合，还是只做 Skill 文档协议，或从第一版就包含库/服务？

### D2. 首个运行环境

建议：**Codex-first、协议工具中立**。先保证在 Codex 项目中可用，但数据模型不出现 Codex 专属节点语义，未来可接其他 Agent。

需要决定：第一版是否只支持 Codex，还是必须同时验证至少一种其他 Agent 运行环境？

### D3. 账本与定义文件格式

建议：**JSONL 事件账本 + YAML/JSON 定义文件 + 生成的 Markdown 人类视图**。JSONL 适合追加和追溯，定义文件适合审阅，Markdown 不作为机器状态的唯一来源。

需要决定：是否接受多格式分工，还是要求单一格式？

### D4. 资源锁的强制程度

建议：对项目内可控资源实施工具强制；对账号、环境和外部会话采用“租约 + 实时探测 + 门禁”，因为本地工具无法保证外部世界没有旁路修改。

需要决定：第一版是强制阻止冲突，还是只报告冲突并由治理者处理？

### D5. 身份与职责隔离的可信等级

建议：v0.1 先采用项目主体 ID、事件签字和 Git/运行通道证据，明确它能证明流程分离但不能提供强密码学身份保证；后续再接认证系统。

需要决定：第一版是否必须具备密码学签名或外部身份认证？

### D6. 默认风险模式

建议：默认使用“标准”模式；只有明确满足低风险条件时才降为“轻量”；生产、数据、安全、费用、权限、外部公开写入、放宽门禁和不可逆操作自动进入“严格”。

需要决定：上述高风险集合是否完整，是否还有业务特有的高风险类别？

### D7. User 授权如何成为锚点

建议：User 在对话或外部系统中的明确决定必须被写成带原文引用、范围、时间和动作摘要的决策事件；无可引用记录则视为未授权。

需要决定：可接受哪些授权通道，以及由谁负责把授权写入账本？

### D8. 单机还是共享协作

建议：v0.1 以单仓库、单机文件系统为边界，不承诺分布式并发安全；通过 Git 交换不可变定义和历史，不把 Git 当作实时锁服务。

需要决定：第一版是否必须支持多台机器同时写账本或领取资源？如果必须，MVP 架构需要升级为带协调服务的方案。

## 15. 确认后的真源拆分建议

本文获批后，不应长期作为包揽一切的单一真源。建议拆分为：

- 产品合同：定位、目标、非目标、适用场景和 v0.1 范围；
- 治理合同：四层权限、风险、User 授权和规则生命周期；
- 系统图规范：节点、边、不变量、状态机和 Schema；
- 操作协议：冷启动、恢复、资源、门禁、读回和升级；
- 决策记录：D1–D8 的 User 裁决及后续替代关系；
- 运行账本：仅在实现阶段建立，记录真实事件和证据。

未来 `SKILL.md` 只指向这些真源并给出确定性发现顺序，不复制其全文。
