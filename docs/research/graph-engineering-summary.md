# Graph Engineering 说明

## 1. 定义

Graph Engineering 是一种面向多 Agent、长周期和高并发软件项目的工作系统设计方法。

它不把开发过程理解成一条简单的任务流水线，而是把项目建模为一张由以下元素组成的运行图：

- **节点**：角色、真源、门禁、资源、通道和外部决策者；
- **边**：派发、交付、验证、否决、打回、合流、升级、回滚和恢复关系；
- **回路**：执行、质量、治理、审计以及它们之间的反馈；
- **锚点**：不能由当前执行者自行改写的产品目标、真实运行和不可变证据；
- **节奏**：分钟级执行、小时级巡检、天周级版本收口以及更慢的战略决策。

其核心主张是：

> 单个反馈循环只是系统中的一块积木。真正需要设计的是一张能够互相监视、互相约束和互相纠正的回路网络。

## 2. 解决的问题

Graph Engineering 主要解决传统任务列表和单 Agent 工作流难以覆盖的问题。

### 2.1 Agent 自报不可直接信任

Worker 可能报告“已经完成”，但实际存在：

- 测试被跳过；
- 只验证源码，没有真实运行；
- 使用假数据或 Mock 代替真实路径；
- 服务运行的是旧代码；
- 修改了配置，但进程读取的是另一份配置；
- 交付回执遗漏关键风险；
- 分支继续变化，评审对象却没有固定。

Graph Engineering 要求使用独立质量回路、不可变锚点、真实运行和读回证据，而不是依赖执行者总结。

### 2.2 多 Agent 并发产生资源冲突

多个 Worker 可能竞争：

- 同一个文件或工作树；
- 端口、数据库和测试账号；
- 浏览器登录会话；
- E2E 执行窗口；
- 迁移编号和共享 Schema；
- 同一个部署或发布环境；
- 有限的 Agent 会话和模型额度。

Graph Engineering 将这些运行时对象显式建模为资源节点，并规定互斥、排队、让渡和现查机制。

### 2.3 新输入破坏在途工作

用户的新想法、纠偏、问询、授权和临时需求不应自动插入当前施工。

系统必须判断：

- 这是需要立即执行的命令吗；
- 是否改变当前工作范围；
- 是否改变项目规则；
- 是否只需要回答而不修改工序；
- 是否需要排到下一版本窗口；
- 是否需要更高权限裁决。

### 2.4 内部指标与真实结果脱节

测试绿色、任务完成数和合流速度都可能被局部优化，但用户仍然无法完成实际任务。

Graph Engineering 使用真实运行锚点和反向指标，防止代理指标冒充最终结果。

### 2.5 系统无法跨会话稳定接班

如果状态只存在于某个 Agent 的上下文中，会话中断后就无法可靠恢复。

Graph Engineering 要求项目能够从真源、账本、不可变锚点和恢复手册重新冷启动。

## 3. 四层反馈回路

Graph Engineering 的组织核心是执行、质量、治理和审计四层回路。

### 3.1 执行回路

执行回路负责：

- 接收目标和边界；
- 在隔离分支或工作树中实施；
- 添加开发者测试；
- 生成提交、精确 diff 或其他不可变交付锚点；
- 报告已验证、未验证、风险和外部副作用。

执行回路的目标是快速产生可以被独立检查的结果，而不是自行宣布最终完成。

### 3.2 质量回路

质量回路负责：

- 独立代码评审；
- 测试正常、边界、异常、无权限和回归路径；
- 真实浏览器、真实数据库和真实服务验证；
- 检查测试跳过、假数据和证据完整性；
- 对不满足标准的交付行使否决权。

执行者自报成功不等于质量通过。任何修复都必须产生新锚点，并重新执行受影响的评审和测试。

### 3.3 治理回路

治理回路负责：

- 分析范围和非目标；
- 拆分任务包；
- 选择 Worker；
- 分配文件和资源所有权；
- 定义验收判据；
- 控制依赖、并发、合流和发布顺序；
- 处理阻塞和升级；
- 维护项目状态真源。

治理回路不能用调度权替代独立质量结论，也不应静默修改工程师交付结果。

### 3.4 审计回路

审计回路检查的对象包括执行、质量和治理三层，而不只是开发工程师。

它负责：

- 检查项目状态和真源是否仍然新鲜；
- 检查质量指标是否对应真实结果；
- 判断问题应归因于需求、架构、执行、测试、环境还是治理；
- 识别重复事故和失效规则；
- 提出流程、门禁和规则修复；
- 在证据充分时阻塞受影响的交付范围。

审计必须保持独立，不能同时提出、批准、应用和验证自己的规则。

## 4. 回路之间的边

四层回路的价值来自它们之间明确的约束关系。

### 4.1 质量否决执行

质量回路打回的交付不得合流或发布。执行者不能通过修改自己的总结绕过失败结论。

### 4.2 治理定义质量判据

任务派发前必须说明如何判断完成，例如：

- 需要通过哪些测试；
- 必须走通哪些用户路径；
- 需要验证哪些失败状态；
- 哪些数据、迁移或环境读回必须提供；
- 哪些动作禁止执行。

### 4.3 审计可以纠正治理

如果任务拆分、验收标准、资源安排或合流策略本身错误，审计应把问题归因于治理层，而不是继续要求执行者返工。

### 4.4 快回路不能改写慢回路目标

执行、巡检和日常调度可以快速运行，但不能自行修改：

- 已批准的产品范围；
- 架构和数据合同；
- 用户裁决；
- 强制门禁；
- 生产和费用授权边界。

需要改变这些内容时，应升级到对应的慢层决策者。

### 4.5 升级而不是覆盖

Worker 遇到超出权限的问题时，应停止在只读或安全状态，提交最小决策项，而不是按照自己的猜测覆盖原决定。

## 5. 真源

真源是某个事实领域中，拥有明确适用范围、优先级、写权限和生效状态，并在发生冲突时作为最终判断依据的信息来源。

一个项目通常有多个领域真源：

| 领域 | 真源示例 |
| --- | --- |
| 产品目标 | 已批准的 PRD 或产品合同 |
| 技术架构 | 当前有效的 ADR 或架构合同 |
| API 和数据 | Schema、接口合同、正式数据库 |
| 视觉设计 | 项目批准的设计源 |
| 当前代码 | 接受的 Git commit |
| 当前部署 | 运行环境版本和配置读回 |
| 项目状态 | 编排账本或权威看板 |
| 用户决定 | 裁决记录或授权引用 |
| 项目工作规则 | 当前已应用并有效的规则文件 |

真源不等于“最新修改的文件”，也不等于“当前代码已经这样实现”。草稿、截图、旧分支、Worker 总结、Agent 记忆和自动摘要只能作为线索或证据，不能自动覆盖已批准真源。

## 6. 外部锚点

Graph Engineering 通过外部锚点防止系统自我验证、自我合理化和自指漂移。

### 6.1 用户和最终决策者

技术验证通过不等于产品体验、风险和商业目标已经获得最终确认。

### 6.2 真实运行

真实浏览器、真实接口、真实数据库和真实用户路径比源码搜索和模拟结果更可靠。

### 6.3 不可变版本

评审、测试、合流和发布必须引用 commit、tag、制品摘要或精确 diff，而不是会继续移动的分支名。

### 6.4 完整门禁数字

测试结果应记录总数、通过、失败和跳过。只报告“零失败”会掩盖全部关键测试被跳过的情况。

### 6.5 反向指标

任何主指标都应配套能够揭示其失真的反向指标：

| 主指标 | 反向指标 |
| --- | --- |
| 合流数量 | 打回率、返工率 |
| 测试通过数 | skip 数、变异咬合率 |
| 交付速度 | 用户可感知变化 |
| 任务数量 | 决策等待和阻塞时间 |

## 7. 节点模型

一个完整的 Graph Engineering 项目通常包含以下节点。

### 7.1 角色节点

包括执行者、评审者、测试者、治理者、审计者和最终授权者。

角色是权限和职责节点，不一定与某个固定模型或人员永久绑定。

### 7.2 真源节点

包括产品合同、架构合同、决策记录、版本计划、项目状态账本和规则文件。

每个真源必须明确适用范围和写权限。

### 7.3 门禁节点

包括代码检查、测试、构建、架构守卫、真实用户路径、迁移安全、部署读回和生产授权。

门禁失败必须有明确的打回或停止边。

### 7.4 资源节点

包括端口、数据库、账号、浏览器会话、测试窗口、迁移编号、工作树写权、部署环境和模型会话。

资源节点需要互斥类型、现查方法和让渡规则。

### 7.5 通道节点

包括 Agent 会话、任务文件、消息系统、Issue、收件箱、事件队列和人工批准通道。

通道必须区分“已经发送”和“对方真实收到并开始执行”。

## 8. 输入闸

输入闸用于保护正在执行的工作，使新输入沿确定路径进入系统。

可以将输入分为：

- 明确授权或执行命令；
- 新需求或新想法；
- 对当前结果的纠偏；
- 项目机制和规则变化；
- 状态问询；
- 账号、凭据和外部资源；
- 隐含命令或需要澄清的表达。

默认原则是：

> 新输入不直接修改在途工序，除非它属于生产事故、明确紧急命令、用户叫停或项目定义的其他即时条件。

如果输入与已有决定冲突，系统应明确指出冲突并请求收敛，而不是静默采用最新一句话。

## 9. 资源和并发控制

Graph Engineering 不只管理文件冲突，也管理运行时资源冲突。

### 9.1 一写者原则

同一文件、迁移、Schema、部署配置或共享清单在同一时间只能有一个写者。

### 9.2 状态型测试串行

共享账号、数据库、端口、浏览器会话和可变环境的测试不能盲目并发。

### 9.3 发出前现查

对于变化快的资源状态，静态登记不足以证明当前可用，应在派发、迁移、测试或部署前重新检查。

### 9.4 异步动作使用不可变引用

后台合流、测试、部署和发布必须引用不可变对象，防止异步执行期间目标继续移动。

## 10. 环境水位和运行读回

配置文件正确不代表运行进程使用了正确配置，代码已构建也不代表服务运行了对应版本。

运行读回应至少确认：

- 代码或制品版本；
- 环境配置指纹；
- 数据库和迁移水位；
- 服务健康状态；
- 登录或权限路径；
- 新增路由或关键用户路径；
- 日志、指标和告警状态。

发布成功应以读回结果为准，而不是以部署命令退出码为准。

## 11. 节奏分离

不同类型的决策应运行在不同时间尺度上。

### 快节奏

分钟到小时级，负责：

- Worker 判活；
- 当前任务推进；
- 验收和打回；
- 资源排队；
- 安全范围内的重新派发。

### 中等节奏

天到周级，负责：

- 阶段收口；
- 版本总结；
- 质量和返工分析；
- 计划微调。

### 慢节奏

周到月级，负责：

- 产品方向；
- 版本优先级；
- 重大架构变化；
- 权限和风险边界；
- 系统规则重构。

慢层决定约束快层执行。快层发现目标可能错误时，应上报而不是自行修改。

## 12. Worker 路由

Graph Engineering 可以按照任务需要为 Worker 建立能力画像，而不是只按传统职位派工。

常用画像维度包括：

- 上下文范围；
- 工具和系统权限；
- 技能和领域知识；
- 模型推理与执行能力；
- 可访问的运行资源；
- 决策和门禁权限；
- 成本与延迟；
- 风险边界。

路由时通常按照以下顺序判断：

1. 风险边界是否允许；
2. Worker 是否拥有必要上下文；
3. 工具和权限是否满足；
4. 能力是否匹配；
5. 是否可以使用成本更低的 Worker；
6. 质量和最终签字权是否仍然独立。

## 13. 自进化与规则自愈

Graph Engineering 要求系统根据真实结果调整自身，而不是只完成产品任务。

典型自进化回路是：

```text
真实事故或新知
→ 复盘和归因
→ 规则或门禁提案
→ 独立批准
→ 应用到模板、流程或守卫
→ 后续真实交付验证
```

新增规则前应判断问题究竟属于：

- 现有规则未执行；
- 责任归属不清；
- 证据缺失；
- 工具或环境故障；
- 现有规则确实不足。

如果现有规则已经足够，就不应通过新增规则掩盖执行问题。

规则自愈也必须包含删除、合并和失效验证，防止历史事故不断堆积成永久复杂度。

## 14. 已知失效模式

### 14.1 代理指标冒充结果

只统计测试数量、任务数量、提交数量或文档数量，而不检查真实用户价值。

### 14.2 绿色门禁掩盖 skip

门禁显示零失败，但关键验证全部被跳过。

### 14.3 回执遗漏风险

Worker 没有故意虚报，但遗漏了边界、失败状态、未验证项或外部副作用。

### 14.4 心跳制造虚假忙碌

为了每轮都有产出而持续创建任务和文档，反而不再核对旧账和真实结果。

### 14.5 审计只审下层

把治理、任务设计和验收标准的问题归咎于执行者，导致重复换人却不修系统。

### 14.6 统筹节点成为瓶颈

如果拆包、派发、裁决、验收、合流和真源更新全部集中在一个角色，会造成决策排队和单点失效。

### 14.7 规则持续膨胀

每次事故都增加永久门禁，最终使 Worker 的主要工作变成满足流程，而不是交付价值。

## 15. 优点

- 对多 Agent 并发和运行资源竞争有较强控制能力；
- 能抵抗 Worker 自报、假绿色和内部自证；
- 能保护在途工作不被新输入随意破坏；
- 能从真实事故中修复流程和门禁；
- 通过不可变锚点和真实运行提高证据可信度；
- 通过快慢节奏分离保护长期目标；
- 适合复杂、长期、高风险、需要跨会话接班的项目。

## 16. 缺点

- 系统概念和操作成本较高；
- 需要维护真源、账本、资源、门禁和恢复机制；
- 容易形成中心化治理瓶颈；
- 高频巡检、独立验证和审计会增加模型与时间成本；
- 项目专用资源和通道规则难以直接复制；
- 看板和文档失去新鲜度后可能制造虚假确定性；
- 如果缺少规则清理机制，容易过度工程化。

## 17. 适用场景

Graph Engineering 适合：

- 多个 Agent 或 Worker 长期并行工作的项目；
- 涉及数据库、云环境、浏览器、部署和共享测试资源；
- 对生产、费用、数据和权限风险敏感；
- 需要持续交付、跨会话接班和高频运行控制；
- 内部测试结果容易与真实用户结果脱节。

对于低风险、容易回滚和影响范围很小的任务，可以压缩回路，但仍应保留不可变锚点、独立验证和明确授权。

## 18. 与 DevSwarmSkill 的关系

Graph Engineering 和 DevSwarmSkill 关注的问题不同但可以互补。

| Graph Engineering 回路 | DevSwarmSkill 角色 |
| --- | --- |
| 执行 | Development Engineer、Operations Engineer |
| 质量 | Reviewer、Tester |
| 治理 | Orchestrator、Product Manager、Architect |
| 审计 | Project Audit |

DevSwarmSkill 更适合作为通用治理内核，提供：

- 稳定角色槽位；
- 项目真源发现；
- 追加式角色看板；
- 不可变交付锚点；
- 独立 Review、Test 和 Operations；
- 跨域风险分级；
- 四态规则生命周期；
- 治理结构校验。

Graph Engineering 更适合作为项目运行扩展，提供：

- 输入闸；
- 高频心跳；
- 资源注册和现查；
- 通道验活；
- 真实浏览器和数据验证；
- 环境水位读回；
- 反向指标；
- Worker 能力、成本和风险画像。

推荐组合是：

```text
DevSwarmSkill 通用治理内核
        +
项目自己的产品、架构和设计真源
        +
Graph Engineering 项目运行扩展
```

## 19. 实施建议

第一次在项目中采用 Graph Engineering 时，不应一次建立全部机制，可以按照以下顺序逐步生长：

1. 明确项目真源和优先级；
2. 使用不可变提交或制品作为交付锚点；
3. 分离执行、独立 Review 和独立 Test；
4. 建立共享资源和单写者规则；
5. 增加测试环境、部署和配置读回；
6. 建立输入闸和在途工作保护；
7. 根据真实事故增加必要门禁；
8. 建立审计、复盘和规则生命周期；
9. 定期删除失效规则和归档历史记录。

每增加一个机制，都应能回答：

- 它解决了什么已经发生或明确存在的问题；
- 它由谁维护；
- 如何验证它确实有效；
- 它带来的成本是什么；
- 什么条件下应当简化或删除。

## 20. 总结

Graph Engineering 的本质可以概括为：

> 把多 Agent 软件项目设计成一张有真源、有资源、有权限、有否决、有升级、有恢复和有自我纠正能力的运行图。

它追求的不是让每个 Worker 都更忙，而是让整个系统在输入变化、并发竞争、会话中断和局部错误中仍然保持稳定，并持续产生能够被真实环境和用户结果验证的交付。
