# Graph Engineering 四层回路组织方式

## 核心思想

Graph Engineering 的核心不是把团队划分为四个部门，而是建立四个职责独立、运行速度不同、能够互相纠正的反馈回路：

1. **执行回路**：接收任务、实现代码、自测并提交不可变交付物，目标是快速产生可验证结果。
2. **质量回路**：独立执行代码评审、测试、真实运行和变异验证，对执行结果拥有否决权；执行者自报成功不能作为完成证据。
3. **治理回路**：决定工作范围、任务拆分、执行者、验收标准、资源与合流顺序，负责控制项目整体节奏。
4. **审计回路**：检查执行、质量和治理机制本身是否有效，不只审查工程师，也可以推翻错误的任务设计、验收标准或治理决策。

四层之间最重要的约束关系是：

- 质量回路可以否决执行回路；
- 治理回路负责定义质量回路的判据；
- 审计回路可以推翻治理回路的错误判断；
- 快速回路可以执行既定目标，但不能自行修改慢速回路确定的目标、真源或强制门禁；
- 需要更高权限的事项必须升级，而不是由下层回路覆盖原有决定。

因此，四层回路组成的不是单向流水线，而是一张具有验证、否决、打回、升级和自我修正能力的回路网络。

## 外部锚点

四层回路必须依赖不能被当前执行结果自行改写的外部锚点，否则容易出现内部检查全部通过、实际结果却已经偏离项目目标的情况。

典型外部锚点包括：

- 用户或最终决策者对产品体验和风险的判断；
- 真实运行环境、真实数据和真实用户路径；
- 当前有效的需求、架构、设计、计划和决策真源；
- 可以复现的门禁数字、测试结果、变异验证和运行读回证据。

## 优点

### 防止执行者自证成功

执行者不能使用自己编写的总结证明任务完成，必须由独立质量回路检查不可变锚点和真实结果。

这尤其适合 AI Worker，因为 AI 容易出现以下问题：

- 只验证自己熟悉或刚刚实现的路径；
- 把测试文件存在误认为测试有效；
- 忽略跳过的测试、假数据和真实环境差异；
- 使用完成报告代替实际运行证据。

### 提高错误归因准确性

交付失败不一定来自开发工程师，也可能来自需求、架构、任务拆分、验收标准、测试环境或调度错误。

审计回路能够检查治理层，避免把系统性问题全部归因于执行者，也避免通过反复更换工程师掩盖任务设计或治理机制的问题。

### 适合长期、多 Worker 项目

四层回路明确了任务、证据、验收、合流和规则演化之间的关系，可以降低以下风险：

- 多 Worker 并发修改产生冲突；
- 会话中断或上下文丢失后无法接班；
- Worker 自报状态不可信；
- 快速执行破坏长期目标；
- 未验收结果被错误合流或发布。

### 支持系统自愈

重复事故可以进入以下闭环：

```text
事故 → 复盘 → 规则提案 → 批准 → 应用 → 独立验证
```

系统不仅处理当前问题，还尝试修复本应提前发现该问题的流程、规则或门禁。

### 让慢层约束快层

执行和日常调度可以快速推进，但不能自行修改产品目标、项目真源或强制门禁。这可以防止 Agent 为了完成当前任务而偷偷改变“做什么”或“什么算完成”。

## 缺点

### 流程成本较高

工作需要经过执行、独立评审、测试、治理验收和必要审计，会增加：

- Worker 和模型成本；
- 工件、回执及证据数量；
- 上下文和维护成本；
- 交付等待时间。

如果低风险小任务始终运行完整四层流程，治理成本可能超过开发收益。

### 容易形成治理瓶颈

如果任务拆分、派工、验收、合流和裁决集中在同一个治理节点，所有工作都会等待该节点，可能出现：

- 治理角色过载；
- 决策长期排队；
- Worker 已完成但无法合流；
- 审计和汇报持续增加，实际交付速度下降。

### 系统复杂度较高

该模式通常需要维护真源文件、任务账本、Worker 状态、资源登记、验收回执、决策记录、规则和门禁。

如果这些信息失去新鲜度，系统可能表现为流程完整，但内部状态已经不再对应真实项目。

### 可能产生审计递归

审计可以推翻治理，因此还必须明确：

- 谁能审查审计行为；
- 审计错误如何申诉；
- 审计是否可以直接修改规则；
- 审计可以基于什么证据阻塞交付。

审计必须受到独立审批、申诉路径、证据要求和权限边界约束，不能同时提出、批准、应用和验证自己的规则。

### 容易过度工程化

重复事故固化为规则有助于防止复发，但如果每次问题都新增永久门禁，可能导致：

- 规则和例外不断膨胀；
- Worker 主要精力用于满足流程；
- 历史事故长期拖累当前效率；
- 为低概率风险增加不成比例的复杂度。

规则自愈不仅应支持新增规则，也应支持合并、简化、失效验证和移除无效规则。

## 适用范围

四层回路适合以下场景：

- 长期运行、多 Worker 或多 Agent 协作项目；
- 生产风险、数据风险、费用风险或合规风险较高；
- 执行结果容易出现自报失真；
- 需要跨会话接班、持续交付和规则演化。

对于低风险、低影响、容易回滚的小任务，可以压缩质量和治理流程，但仍应保留不可变锚点、独立验证和明确授权边界。

## 与 DevSwarmSkill 的对应关系

在 DevSwarmSkill 中，四层回路可以映射为：

| Graph Engineering 回路 | DevSwarmSkill 角色 |
| --- | --- |
| 执行 | Development Engineer、Operations Engineer |
| 质量 | Reviewer、Tester |
| 治理 | Orchestrator、Product Manager、Architect |
| 审计 | Project Audit |

User 位于四层回路之外，作为产品真源、高风险冲突、规则例外以及费用、生产和不可逆外部动作的最终授权者。

## 总结

四层回路的本质是：

> 让生产结果、验证结果、安排工作和检查系统的人彼此独立，并允许更慢、更高层的反馈回路纠正快速执行回路。

它通过职责隔离、真实证据、否决权、升级机制和规则自愈提高长期项目的稳定性，但必须控制治理成本、集中式瓶颈、文档陈旧和规则膨胀。
