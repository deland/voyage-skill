# Graph Engineering 讨论整理

> 整理日期：2026-08-13
> 文档性质：讨论历史、认知演进与新项目准备材料，不是 DevSwarmSkill 或未来项目的运行真源。

本文整理我们在 DevSwarmSkill 设计过程中围绕 Graph Engineering 的主要讨论。完整概念说明见 [`graph-engineering.md`](graph-engineering.md)，四层回路专题见 [`graph-engineering-four-loop-model.md`](graph-engineering-four-loop-model.md)。

## 1. 讨论起点：项目级入口 Skill

最初参考的 `graph-engineering` Skill 被理解为一个项目工作系统的稳定入口，而不是把全部规则复制进 Skill 的大提示词。

它主要承担四类职责：

1. 指向当前有效的项目真源；
2. 给出接班、巡检、派工、发针、合流和验收的恢复序列；
3. 提供少量高频资源判据和门禁命令；
4. 在每次启动时触发每日调研，推动工作系统持续演化。

由此形成的第一条重要认识是：

> Skill 应是稳定入口和恢复协议，复杂项目的真实状态与完整机制应保存在项目可版本化、可审计的文档和账本中。

原 Skill 采用了四层真源指针：

| 层 | 负责内容 |
| --- | --- |
| 规矩层 | 跨项目协作硬规则和不可违背的行为边界 |
| 结构层 | 节点、边、资源、状态和稳态机制 |
| 操作层 | 命令、判据、接班、恢复和验收序列 |
| 协作层 | 派发结构、工作包流转和团队协作方式 |

此外还有独立账本维护任务、资源、迁移、依赖和运行状态。

这套设计的价值不在于“四份文档”，而在于把不同变化速度、不同写权限和不同责任范围的信息分离，避免单一文档既描述原则、又记录瞬时状态、还承担操作手册。

## 2. “真源”的讨论结论

讨论中对“真源”的定义逐渐收敛为：

> 在某个事实领域内，拥有明确适用范围、优先级、写权限和生效状态，并在冲突时作为最终判断依据的信息来源。

真源不等于：

- 最近修改的文件；
- 当前代码碰巧呈现出的行为；
- Worker 的总结或记忆；
- 截图、旧分支、历史原型或临时工件；
- 未批准的提案或尚未生效的规则。

一个项目可以同时存在多个领域真源，例如产品、架构、设计、API、数据、部署、运行状态和工作规则。关键是每个领域必须明确：

- 谁能写；
- 什么条件下生效；
- 与其他真源冲突时谁优先；
- 如何退役旧真源；
- 如何用命令或证据确认当前版本。

Graph Engineering 对真源的要求比普通文档管理更强：状态只能由命令、不可变锚点和真实读回确认，不能由会话记忆或口头状态覆盖。

## 3. 从流水线到运行图

讨论最重要的认知变化，是不再把多 Agent 开发理解为：

```text
需求 -> 开发 -> Review -> Test -> 完成
```

而是理解为由多种节点和边构成的运行图：

- **角色节点**：执行者、评审者、测试者、治理者、审计者和最终授权者；
- **真源节点**：产品、架构、设计、计划、规则和状态账本；
- **资源节点**：文件、端口、数据库、账号、环境、会话和发布窗口；
- **门禁节点**：测试、构建、架构检查、运行读回和人工验收；
- **通道节点**：Agent 会话、任务文件、Issue、消息和人工投递；
- **外部锚点**：真实用户结果、真实环境、不可变提交和最终授权。

节点之间存在派发、交付、验证、否决、打回、合流、升级、让渡、回滚和恢复等边。

因此，Graph Engineering 的核心不是“让更多 Agent 并行工作”，而是：

> 让任务、状态、资源、权限、证据和恢复路径在多 Agent 并发与会话中断下仍保持一致。

## 4. 高频工程判据带来的启示

原项目实践中有若干具体判据，虽然不能直接复制到通用项目，但揭示了 Graph Engineering 的工程风格。

### 4.1 发出任务前现查资源

不能只根据登记表判断 Worker、会话或环境是否空闲。派发前必须检查真实进程、当前持有人和启动时间，避免残留进程、假匹配或重复会话。

通用结论：

- 资源注册簿用于说明资源类别和冲突规则；
- 当前持有人和可用性必须现查；
- “计划空闲”不能代替“运行时空闲”。

### 4.2 状态型测试必须互斥

共享登录账号、浏览器会话、数据库、端口或环境的 E2E 测试不能并发，否则测试可能互相踢下线或污染数据。

通用结论：

- 资源冲突不只发生在文件；
- 测试账号、端口、环境和数据集都应建模为资源节点；
- 状态型测试需要单活、排队或隔离环境。

### 4.3 异步动作必须引用不可变对象

合流、后台测试、部署或迁移如果引用可移动分支名，执行期间目标可能发生变化。

通用结论：

- 异步动作使用 commit、tag、内容哈希或精确 diff；
- 派发、评审、测试和合流必须指向同一不可变锚点；
- 修复产生新锚点，并使旧结论失效。

### 4.4 服务换代必须真实读回

进程启动或部署命令成功不能证明服务已正确换代。必须读取健康状态、身份或登录状态，以及新版本特有的行为或路由。

通用结论：

- 命令退出码是过程证据，不是最终结果；
- 环境切换需要健康、版本、配置和关键路径读回；
- 真实运行状态应成为独立节点，而不是部署脚本的附属输出。

### 4.5 门禁结果必须保留完整退出语义

通过管道筛选输出可能吞掉前置命令的失败退出码。

通用结论：

- 门禁先把完整结果落到可靠工件；
- 分析结果与执行结果分开；
- 不能用“没有匹配到 fail 文本”替代真实退出状态和测试统计。

## 5. 四层回路：执行、质量、治理、审计

讨论中将 Graph Engineering 的组织核心概括为四个速度不同、可以互相纠正的反馈回路。

| 回路 | 责任 | 核心权力 |
| --- | --- | --- |
| 执行 | 实现、配置、自测、产出不可变交付物 | 快速产生可验证结果 |
| 质量 | 独立 Review、Test、真实运行和缺陷证明 | 否决不合格交付 |
| 治理 | 范围、拆包、派工、资源、顺序、验收判据 | 控制项目整体方向和节奏 |
| 审计 | 检查执行、质量和治理机制是否有效 | 纠正系统性失效并阻塞受影响范围 |

四层之间的关键关系是：

- 质量可以否决执行；
- 治理定义质量判据，但不能替代质量结论；
- 审计可以纠正错误治理，而不只检查开发工程师；
- 快回路可以执行目标，但不能自行修改慢回路确定的目标、真源或强制门禁；
- 超出权限的冲突必须升级，不能由下层静默覆盖。

讨论中特别认可的一点是：审计对象必须包含治理层。任务拆分、验收标准、资源安排或架构判断错误时，不能通过不断要求执行者返工来掩盖系统问题。

## 6. 自进化：每日调研、复盘和规则自愈

Graph Engineering 的自进化能力由三种不同输入组成。

### 6.1 每日调研

目标是观察最近一至三个月的研究、框架发布和工程实践，提前发现下一代工作方式。

调研结果不是直接改规则，而是分类为：

- 可借鉴；
- 不适用；
- 当前体系已领先。

有价值的发现进入正式规则或系统图修订流程。普通调研不应阻塞当前交付。

### 6.2 复盘

复盘基于项目内部的真实结果，寻找：

- 重复缺陷和重复返工；
- 最早应该发现问题的回路；
- 需求、架构、执行、质量、环境、通道或治理层的真实根因；
- 已有规则未执行，还是规则本身不足。

复盘结论不能直接成为强制规则。

### 6.3 规则自愈

讨论最终采用的规则生命周期是：

```text
提出 -> 批准 -> 应用 -> 验证
```

其核心约束是：

- 提出规则的人不能独立批准自己的提案；
- 文档更新只能证明规则已应用，不能证明规则有效；
- 验证必须来自独立 Reviewer、Tester、客观门禁或后续真实交付；
- 规则需要保留来源、成本、风险、验证方式和回滚条件；
- 自愈不仅包括新增规则，也包括合并、简化、失效验证和移除。

由此形成的重要结论是：

> 自进化不是“系统自动修改自己”，而是系统能够发现问题，并通过有权限、有证据、有独立验证的流程安全改变自身。

## 7. 从“项目顾问”到“项目审计”

我们曾考虑增加“项目顾问”角色，负责每日调研、复盘和规则改进。对照 Graph Engineering 后发现，“顾问”只有建议能力，缺少以下关键机制：

- 对治理层的独立检查权；
- 对规则生命周期的管理责任；
- 对证据不足或门禁失效的阻塞权；
- 对自身提案的审批隔离；
- 明确的申诉与解除阻塞路径。

因此角色最终改为 Project Audit，并加入：

- 管理追加式项目规则文件；
- 维护提出、批准、应用、验证四态；
- 基于证据阻塞最小受影响范围；
- 不能审批、应用并验证自己的规则；
- 审计自身争议必须交给独立权威或 User。

这一演进体现了 Graph Engineering 与普通“最佳实践顾问”的差别：前者是带权限边界和反馈闭环的系统节点，后者通常只是信息来源。

## 8. 每日立会与自进化不是同一机制

讨论中增加了所有角色参与的每日立会，但随后明确：每日立会不能替代 Graph Engineering 的自进化回路。

| 机制 | 主要时间尺度 | 解决的问题 |
| --- | --- | --- |
| 每日立会 | 当前日 | 状态同步、阻塞、责任人、下一步 |
| 每日调研 | 日级 | 外部技术和工作方式变化 |
| 复盘 | 事件或周期 | 内部失败模式和根因 |
| 规则生命周期 | 较慢 | 安全改变工作系统 |

立会是协调回路，不应：

- 代替不可变交接和质量证据；
- 通过讨论投票覆盖 Reviewer 或 Tester 的失败；
- 在会议中直接修改高层真源；
- 把未到场角色的意见当作已报告。

立会可以发现重复信号并触发复盘，但规则改变仍必须走完整生命周期。

## 9. 冲突裁决：低风险审计决定，高风险交给 User

讨论中将“所有跨域冲突都升级 User”调整为风险分级：

- 可逆、证据充分且不改变高层真源的低风险冲突，可以由 Project Audit 决定；
- 高风险、不可逆、证据不足或存在角色异议的冲突交给 User。

低风险必须同时满足：

- 可逆且有明确反转条件；
- 不改变产品范围、验收和优先级；
- 不改变公共合同、架构真源或持久接口；
- 不放宽强制门禁；
- 不涉及安全、隐私、凭据和权限；
- 不涉及持久数据、迁移和破坏性操作；
- 不涉及费用、外部写入、发布、部署或生产；
- Product Manager 和 Architect 均无异议；
- Project Audit 与争议行为相互独立。

任何不确定、证据缺失、分类分歧、自我申诉或角色反对都自动升级为高风险。

这一设计被认为可行，但前提是风险分类本身可审计，且 Project Audit 不能裁决针对自身行为的申诉。

## 10. Graph Engineering 与 DevSwarmSkill 的对比结论

讨论多次比较两者，最终形成以下认识。

| 维度 | Graph Engineering | DevSwarmSkill |
| --- | --- | --- |
| 定位 | 项目运行系统和控制图 | 通用软件交付 Skill |
| 核心对象 | 节点、边、资源、真源、门禁、节奏和反馈回路 | 角色、任务、看板、交接和验收流程 |
| 状态管理 | 命令现查、资源账本、运行读回 | 追加式角色看板和不可变锚点 |
| 并发控制 | 文件与运行时资源统一建模 | 通用单写者和冲突资源发现 |
| 自进化 | 每日调研、复盘、系统图和规则修订 | Project Audit 与四态规则生命周期 |
| 项目耦合 | 深度绑定具体项目资源和操作判据 | 主动发现项目规则，内核保持通用 |
| 优势 | 稳态强、恢复强、资源控制细、适合长期多 Agent 项目 | 易安装、易迁移、角色清晰、通用性强 |
| 风险 | 复杂、治理成本高、容易中心化和规则膨胀 | 对运行时资源和输入闸的建模较弱 |

两者不是简单替代关系。讨论中的理想组合是：

```text
通用协作内核
    +
项目自己的产品、架构和设计真源
    +
Graph Engineering 项目运行扩展
```

不过，如果另开一个专门项目模仿 Graph Engineering，新项目应直接以“运行图和控制系统”为核心，而不是先从固定角色工作流出发。

## 11. 被认可的优点

讨论中最值得模仿的能力包括：

1. **跨会话稳定接班**：状态不依赖某个 Agent 的上下文。
2. **执行者不能自证成功**：质量和真实运行拥有独立否决权。
3. **资源成为一等节点**：文件之外的会话、账号、端口和环境也被控制。
4. **慢层约束快层**：日常执行不能偷偷改变产品目标和完成标准。
5. **审计治理本身**：系统性错误不会全部归因于开发者。
6. **异步动作使用不可变锚点**：评审、测试和合流目标不会漂移。
7. **规则可以安全演化**：改变系统本身也需要批准和验证。
8. **真实结果优先**：运行读回和用户结果高于代理指标。

## 12. 需要警惕的缺点

讨论也明确了不能照搬的部分：

- 高频巡检、完整四层流程和多 Worker 会增加成本与等待时间；
- 统筹节点容易成为派工、裁决、合流和验收瓶颈；
- 文档、账本和注册簿失去新鲜度后会制造虚假确定性；
- 审计权过大可能形成新的单点和递归审计问题；
- 每次事故都新增规则会导致规则无限膨胀；
- 项目专用命令、路径、供应商和环境判据不能进入通用内核；
- 小型、低风险、易回滚任务运行完整机制可能得不偿失。

因此未来项目必须支持按风险压缩流程，同时保留不可变锚点、独立验证和授权边界。

## 13. 新项目可采用的核心设计

如果基于本次讨论另开一个 Graph Engineering 项目，建议第一版围绕以下对象设计。

### 13.1 稳定入口

- 一个精简 Skill 或 CLI 作为冷启动入口；
- 只保存发现顺序、恢复序列和真源指针；
- 不复制项目详细状态，避免入口与真实文档漂移。

### 13.2 系统图

- 节点：角色、真源、任务、资源、门禁、环境、通道和外部授权者；
- 边：派发、依赖、交付、验证、否决、合流、升级、让渡和回滚；
- 每类边定义前置条件、证据、权限和失效条件。

### 13.3 状态账本

- 追加式记录任务和关键决策；
- 区分计划状态、声明状态和现查状态；
- 状态更新必须引用命令、不可变锚点或真实读回；
- 支持从账本和仓库证据恢复，而不是依赖会话摘要。

### 13.4 资源控制器

- 发现文件、锁文件、迁移、端口、账号、环境和会话资源；
- 支持独占、共享、串行和可重建资源；
- 派发前现查持有人；
- 支持租约、超时、让渡和异常回收。

### 13.5 四层回路

- 执行、质量、治理和审计拥有独立身份与写权限；
- 质量失败自动使交付回到执行；
- 审计发现治理问题时回到治理，而不是盲目打回执行；
- User 保留高风险、例外和不可逆动作的最终授权。

### 13.6 规则引擎

- 规则具有稳定 ID、领域、作用范围、版本和状态；
- 强制执行提出、批准、应用、验证四态；
- 支持规则合并、替代、失效和移除；
- 审计可以阻塞，但必须记录证据、最小范围和客观解除条件。

### 13.7 运行读回

- 环境准备、部署和发布都有标准化读回；
- 区分命令成功、服务健康、版本正确、配置正确和用户路径可用；
- 将读回结果建模为独立证据，而不是日志中的一句话。

## 14. 建议的第一版范围

为了避免一开始过度工程化，新项目第一版可以只实现：

1. 真源注册与优先级；
2. 节点、边和资源的最小 Schema；
3. 追加式状态账本；
4. 单写者和资源互斥；
5. 不可变锚点；
6. 执行、质量、治理和审计四类回路；
7. 四态规则生命周期；
8. 一个确定性的结构验证器；
9. 冷启动与中断恢复命令。

每日调研、复杂 Worker 路由、自动资源回收、可视化图谱和多项目联邦可以后续增加。

## 15. 新项目前需要回答的问题

在正式开发前，建议先确定：

1. 新项目是 Skill、CLI、库、服务，还是多种形态组合？
2. 系统图和账本使用 Markdown、JSON、数据库还是事件日志？
3. 哪些状态必须通过命令现查，哪些允许由角色声明？
4. 资源锁是建议性规则，还是由工具强制执行？
5. 如何验证 Worker 身份、通道送达和真实开始执行？
6. 审计阻塞如何申诉，谁能解除错误阻塞？
7. 规则如何退役，如何防止历史规则永久膨胀？
8. 哪些低风险工作可以压缩质量或治理回路？
9. 如何证明运行读回对应正确制品、配置和环境？
10. 通用内核与项目扩展的边界放在哪里？

## 16. 讨论形成的最终判断

本轮讨论对 Graph Engineering 的最终判断是：

> 它不是一组多 Agent 提示词，也不是更复杂的任务看板，而是一种把软件项目设计成可验证、可否决、可恢复、可升级和可自我纠正运行图的方法。

最值得为新项目保留的不是原项目中的具体命令和路径，而是以下结构：

- 真源有范围和优先级；
- 资源有持有人和互斥关系；
- 状态由证据确认；
- 异步工作引用不可变对象；
- 执行、质量、治理和审计相互独立；
- 快回路不能改写慢回路目标；
- 规则改变本身也必须被批准和验证；
- 系统最终由真实运行和用户结果校准。

这些原则可以作为另一个 Graph Engineering 项目的立项输入，但正式开发前仍应重新确定产品定位、最小范围、数据模型和运行载体。
